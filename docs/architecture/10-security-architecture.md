# Security Architecture

## Overview

CareerVerse AI handles user accounts, career profiles, learning progress, resumes, interview responses, and AI conversations.

Security must therefore be built into the system from the beginning rather than added after implementation.

---

# Security Goals

The application should provide:

- Secure authentication
- Strong authorization
- Protection of user data
- Secure API communication
- Secure password storage
- Protection of AI credentials
- Input validation
- Protection against common web attacks
- Secure handling of user-generated content
- Auditability of important security events

---

# Authentication

Authentication will be handled by the Spring Boot backend.

Initial approach:

```text
User
  |
  v
Login / Register
  |
  v
Spring Boot Authentication
  |
  v
Authenticated Session
```

The application should support:

- Email/password authentication
- Secure password hashing
- Logout
- Session expiration
- Password reset

Future:

- Google OAuth
- GitHub OAuth
- Multi-factor authentication

---

# Password Security

Passwords must never be stored as plaintext.

The backend will store only a secure password hash.

Example:

```text
Password
   |
   v
Password Hashing Algorithm
   |
   v
Stored Password Hash
```

Recommended implementation:

- BCrypt or Argon2
- Unique salt
- Never log passwords
- Never return password hashes through APIs

---

# Authorization

Authentication answers:

> Who is the user?

Authorization answers:

> What is the user allowed to access?

Every protected backend resource must verify ownership or permission.

Example:

```text
GET /api/v1/roadmaps/123
```

The backend must verify that roadmap `123` belongs to the authenticated user.

The frontend must never be trusted to enforce authorization.

---

# API Security

All production API traffic must use HTTPS.

Protected APIs require authentication.

Security controls include:

- Authentication
- Authorization
- Input validation
- Rate limiting
- Request size limits
- Secure headers
- CORS configuration
- Error handling

---

# Input Validation

All user input must be validated on the backend.

Examples:

- Email format
- Password requirements
- Date ranges
- Skill proficiency levels
- Roadmap IDs
- Interview answers

Never rely only on frontend validation.

Frontend validation improves user experience.

Backend validation provides security.

---

# SQL Injection Protection

Database queries should use:

- Spring Data JPA
- Parameterized queries
- Prepared statements

User input must never be directly concatenated into SQL queries.

---

# XSS Protection

User-generated content such as:

- AI conversations
- Resume content
- Interview answers
- Profile information

must be safely rendered.

The application should avoid injecting untrusted HTML directly into the DOM.

---

# CSRF Protection

The authentication strategy must be selected carefully based on how credentials are stored.

If authentication uses secure cookies:

- Enable appropriate CSRF protection.
- Use Secure cookies.
- Use HttpOnly cookies.
- Use SameSite policies.

If a different token strategy is selected, the CSRF model must be reviewed accordingly.

---

# CORS

Only trusted frontend origins should be allowed to access the backend.

Development:

```text
http://localhost:3000
```

Production:

```text
https://careerverse.ai
```

CORS should never be configured as:

```text
Allow-Origin: *
```

for authenticated production APIs.

---

# Secrets Management

The following must never be committed to Git:

- LLM API keys
- Database passwords
- OAuth secrets
- JWT signing secrets
- Email service credentials

Use environment variables or a dedicated secret-management solution.

Example:

```text
LLM_API_KEY=********
DATABASE_URL=********
DATABASE_PASSWORD=********
```

A `.env` file containing secrets must be included in `.gitignore`.

A safe template may be committed:

```text
.env.example
```

---

# AI Security

AI introduces additional security concerns.

The system must protect against:

- Prompt injection
- Sensitive information leakage
- Malicious user instructions
- Untrusted retrieved content
- Excessive AI usage
- Unauthorized AI access

The AI should never automatically execute arbitrary instructions generated by a user or LLM.

---

# AI Data Privacy

Only the minimum required user information should be sent to an LLM provider.

For example:

```text
User Profile
     |
     v
Context Filtering
     |
     v
Only Relevant Data
     |
     v
AI Provider
```

Sensitive information should not be included unnecessarily.

---

# AI Output Validation

LLM responses should not automatically be treated as trusted application data.

For example, if the AI generates a roadmap:

```text
LLM
 ↓
Structured Response
 ↓
Schema Validation
 ↓
Business Validation
 ↓
Database
```

Invalid or unsafe responses must be rejected or corrected.

---

# Rate Limiting

AI endpoints should have stricter rate limits than normal APIs because they can be expensive.

Examples:

```text
Normal API
→ Higher request limit

AI API
→ Lower request limit

Authentication API
→ Brute-force protection
```

Future versions may introduce usage quotas for different subscription tiers.

---

# File Upload Security

Future uploads may include:

- Resumes
- Certificates
- Profile images

Uploaded files should be:

- Type validated
- Size limited
- Malware scanned where appropriate
- Stored outside executable directories
- Given generated filenames
- Access-controlled

---

# Logging and Monitoring

The backend should log important security events.

Examples:

- Login failures
- Successful authentication
- Password changes
- Unauthorized access attempts
- Rate-limit violations
- Important administrative actions

Logs must not contain:

- Passwords
- API keys
- Authentication tokens
- Sensitive personal information

---

# Error Handling

Production errors should not expose:

- Stack traces
- Database credentials
- SQL queries
- Internal implementation details
- API keys

The API should return safe, structured error responses.

Example:

```json
{
  "status": 401,
  "error": "UNAUTHORIZED",
  "message": "Authentication required"
}
```

---

# Database Security

Production database access should use:

- Strong credentials
- Least-privilege database users
- Encrypted connections where appropriate
- Restricted network access
- Regular backups
- Migration management

The application should not connect using a PostgreSQL superuser in production.

---

# Dependency Security

Project dependencies should be regularly reviewed for known vulnerabilities.

Security updates should be applied through controlled dependency upgrades.

---

# Security Principles

CareerVerse AI follows:

- Defense in depth
- Least privilege
- Secure defaults
- Zero trust between client and server
- Minimize sensitive data
- Validate all external input
- Never trust LLM output automatically
- Keep secrets out of source control

---
